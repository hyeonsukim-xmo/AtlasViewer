# EXMO Desktop·Web 영상 분석 서비스 구현 방향

- 작성일: 2026-09-24 (Asia/Seoul)
- 최종 상태 갱신: 2026-09-26 — Web·Windows Desktop 뷰어 구현, 영상 분석·회원·비교 기능은 계획 단계
- 현재 구현 기준: `design/marimo-glass` / `eca2152` (최초 문서 기준 `0297125`)
- 대상: 현재 EXMO Segmentation Atlas를 기반으로 발전시킬 Desktop·Web 서비스

이 문서는 사용자와 논의한 제품 목표, 유지할 동작, 구현 제안, 미결정 사항을 기록한다. **문서 작성 요청은 아래 기능을 즉시 개발하거나 배포하라는 지시가 아니다.** 기술 후보와 개발 순서는 제안이며, 확정된 구현이나 제공 가능한 성능으로 해석하지 않는다.

구현을 시작할 때는 [개발 준비·변경 경계·회귀 검증 문서](EXMO_DEVELOPMENT_READINESS.md)를 먼저 읽는다. 이후 구체화된 Series preview·바둑판 리뷰·최대 3개 비교 요구는 [영상 워크플로 검토](EXMO_IMAGING_WORKFLOW_REVIEW_2026-09-25.md)에 있다.

## 1. 제품 목표와 핵심 흐름

사용자는 Desktop App에서 X-ray·MRI·CT 검사를 가져와 분석하고, 근육과 뼈의 segmentation 결과를 3D로 확인하려 한다. 구조별 부피, 지방 관련 지표, 좌우 차이와 시간에 따른 변화를 함께 보고, 회원 계정으로 웹에서도 허용된 검사 결과를 열람·비교하는 서비스가 목표다.

현재 AtlasViewer는 이 서비스의 **공통 결과 뷰어**로 발전시킨다. Desktop과 Web이 동일한 검사 결과와 표시 규칙을 사용하도록 하고, 분석 실행과 저장·동기화를 연결한다.

```text
환자 선택 또는 등록
  → 검사 가져오기·입력 확인
  → 영상 조건에 맞는 분석 실행
  → segmentation mask·측정 결과·표시용 3D 생성
  → 결과 확인·저장
  → 선택한 데이터 동기화
  → 웹 열람·동일 환자의 이전 검사와 비교
```

초기 성공 기준은 준비된 영상 종류 하나에서 이 흐름이 실제 데이터로 동작하는 것이다. 모든 영상 종류, 분석 모델, 배포 환경을 처음부터 동시에 지원하는 것은 첫 구현 범위로 제안하지 않는다.

## 3. 현재 저장소의 실제 상태

### 3.1 구현된 범위

현재 저장소는 React·Three.js·Vite로 구성된 단일 케이스 프런트엔드다. `public/models/exmo-1001921.glb`를 로드하며 27개 class를 사용한다. 회원, 환자 DB, 업로드 API, 분석 실행 서버 없이 동작한다. 실행 방법과 기존 검증 범위는 [README](../README.md)에 있다.

같은 프런트엔드를 Electron으로 패키징한 Windows x64 Desktop 버전도 있다. 모델·폰트·브랜드를 번들로 제공하며 별도 서버 없이 데모를 연다. 필요한 때만 화면 주기에 맞춰 렌더링하고 idle/최소화 시 장면 렌더링을 멈춘다. Windows 개발용 설치 파일 생성과 실행 검증까지 완료했으며 운영용 코드 서명·자동 업데이트는 미구현이다.

| 기능 | 현재 동작과 유지할 기준 |
| --- | --- |
| 구조 목록 | 27개 class, Lower Body 24개, 이름·ID·그룹 검색 |
| 조립 상태 | 개별 class 복수 선택·재클릭 해제, 배경 클릭·Esc로 전체 해제 |

## 4. 권장 구성과 책임

### 4.1 공통 결과 뷰어

Desktop과 Web에서 현재 React/Three.js 화면과 표시 규칙을 공유한다. 검사 식별 정보, 구조 목록, 모델, 측정 결과를 받아 표시하는 방향으로 확장한다. 파일 선택, 분석 실행, 로그인처럼 환경에 따라 달라지는 부분을 결과 뷰어의 계산 로직에 섞지 않는다.

처음부터 별도 UI 프레임워크나 범용 플러그인 시스템을 만들 필요는 없다. 두 환경이 실제로 공유하는 코드를 추출하고, 측정 표와 hover는 같은 결과를 읽게 한다.

### 4.2 Desktop

Electron을 채택해 현재 웹 UI를 Windows x64 앱으로 패키징했다. `desktop/main.cjs`가 sandbox와 context isolation을 유지하면서 `atlas://app/`로 번들 자산을 제공한다. 로컬 영상 파일 접근, preload/분석 IPC, 모델 실행은 아직 연결하지 않았다. 다른 OS 지원은 별도 검증 대상이다. [Electron 공식 프로세스 문서](https://www.electronjs.org/docs/latest/tutorial/process-model)

후속 Desktop 기능의 책임은 입력 선택, 분석 요청·상태 표시·취소, 로컬 결과 저장, 결과 확인과 동기화 요청이다. 무거운 영상 처리와 모델 실행은 화면을 그리는 프로세스에서 직접 하지 않는다. 분석 프로세스의 실패가 UI 종료와 이전 결과 손실로 이어지지 않도록 한다.

기존 분석 코드가 Python이라면 Python 실행 프로그램을 별도 프로세스로 연결하는 구성이 우선 후보다. Electron의 `utilityProcess`는 Node.js 프로세스이므로 Python 실행기와 동일시하지 않는다. 외부 실행 파일은 비동기 child process 실행 등으로 연결할 수 있다. 실제 전달 방식은 프로그램을 확인한 뒤 정한다. [Node.js child process 문서](https://nodejs.org/api/child_process.html)

### 4.3 분석 프로그램

입력 영상과 분석 설정을 받아 segmentation mask, 측정 결과, 표시용 모델, 실행 정보를 만든다. UI 상태나 로그인 화면을 알 필요는 없다.

초기에는 **기존 모델이 안정적으로 실행되는 한 환경**을 기준으로 연결한다. 사용자 PC의 GPU에서 실행할지, 서버에서 실행할지는 모델 크기·필수 GPU·설치 조건을 확인한 뒤 결정한다. Desktop 중심 제품이라는 목표가 모든 PC에서 로컬 추론이 가능하다는 의미는 아니다.

로컬 실행과 클라우드 실행을 모두 지원하는 추상화나 GPU 작업 클러스터를 먼저 만들지 않는다. 첫 실행 경로가 완성된 후 실제 배포 필요에 따라 확장한다.

### 4.4 서버와 Web

서버는 계정·접근 권한, 환자·검사·분석 결과의 관계, 파일 저장 위치와 동기화 상태를 관리한다. 초기 구성은 단일 백엔드 API, 관계형 DB, 비공개 파일 저장소 정도로 시작하는 방향을 제안한다. 구체 제품과 호스팅 사업자는 미정이다.

계정 기반 Web은 로그인 후 권한이 있는 결과를 받아 공통 뷰어로 표시하는 방향이다. 이후 사용자가 웹 데모에도 영상 가져오기·분석 흐름을 요청했으며, 상세 요구는 영상 워크플로 검토 문서에 기록했다. 실제 파일 처리와 모델 실행 위치·서버 전송 범위는 아직 결정하지 않았다.

## 5. 영상 입력과 분석 범위

### 5.1 공통 UX와 서로 다른 분석 과정

사용자는 같은 서비스에서 영상을 가져오고 결과를 확인한다. 내부에서는 modality, 촬영 부위, MRI sequence 등 지원 조건에 맞는 분석을 선택한다. 지원하지 않는 입력을 형식만 변환해 지원하는 것처럼 표시하지 않는다.

| 입력 | 구현 방향 | 먼저 확인할 내용 |
| --- | --- | --- |
| CT | 지원 모델로 mask를 만들고 원본 공간 정보를 사용해 측정·3D 생성 | 촬영 범위, 모델 입력 조건, 지원 class, 계산식 |
| MRI | 지원 sequence·필요 series를 확인한 뒤 해당 분석 실행 | 필요한 영상 조합, 공간 정합, 지원 class와 지표 |
| 일반 2D X-ray | 2D 분석과 3D 재구성·추정을 별도 작업으로 정의 | 제공할 결과, 준비된 모델, 검증 데이터와 성능 |
| 이미 생성된 segmentation | 제공된 mask·원본 공간 정보·측정 결과를 연결 | 원본 영상과의 대응, label·좌우·단위·출처 |

TotalSegmentator는 CT와 MRI 작업을 구분하고, thigh 관련 작업에도 개별 근육 대신 compartment 수준 출력이 포함된다. 따라서 외부 모델 하나를 연결하면 현재 27개 class가 그대로 나온다고 가정하지 않는다. 일부 작업은 별도 라이선스 대상이다. 이 도구는 구조를 설명하는 참고 사례이며 채택 결정이 아니다. [TotalSegmentator 공식 저장소](https://github.com/wasserth/TotalSegmentator)

X-ray에서 근육과 뼈를 분리하는 연구는 있지만, 2D 분리 결과가 환자별 3D 근육·부피를 직접 제공한다는 의미는 아니다. X-ray의 3D 결과를 제공하려면 별도 재구성·추정 방식과 검증 범위를 정해야 한다. [방사선 영상의 근골격 분리 연구](https://www.nature.com/articles/s41598-023-35075-x)

### 5.2 가져오기 절차

1. 원본 파일을 읽고 환자·검사·series 관계와 지원 형식을 확인한다.
2. 분석에 사용할 series를 식별한다. 같은 폴더의 모든 영상을 무조건 한 볼륨으로 합치지 않는다.
3. 공간 정보·크기·단위와 모델 입력 조건을 확인한다. 파일 확장자만으로 modality를 단정하지 않는다.
4. 연결할 환자와 검사 날짜를 사용자에게 확인 가능한 형태로 보여준다.
5. 원본을 보존한 상태에서 분석용 입력을 만든다. 변환·재배열·resampling 정보는 결과에 연결한다.

DICOM·NRRD·NIfTI 전체 변형을 첫 버전에서 지원한다고 선언하지 않는다. 첫 모델의 실제 입력 형식부터 정하고, 지원 목록과 실패 이유를 명확히 한다.

## 6. 데이터 구조: 환자·검사·분석 결과

다음은 필요한 의미를 정리한 논리 구조다. 확정 DB schema나 API 명세는 아니다.

| 대상 | 보존할 정보 | 이유 |
| --- | --- | --- |
| 계정·소속 | 사용자 ID, 기관 또는 작업 공간 소속, 권한 | 누가 어떤 자료를 볼 수 있는지 판단 |
| 환자 | 서비스 내부 ID, 소속 범위, 원본 식별자와의 대응 | 이름이 같은 사람이나 기관 간 ID 충돌 방지 |
| 검사 | 환자 ID, 실제 촬영 날짜·시간, modality, 부위, 원본 검사 식별 정보 | follow-up의 기본 단위 |
| Series·입력 | 검사 ID, 촬영 조건, 이미지 크기, 좌표계·affine·단위, 원본 참조 | 여러 series의 구분과 측정 근거 |
| 분석 실행 | 입력 참조, 모델·계산 버전, 설정, 실행 환경, 시작·종료·오류 상태 | 결과 재현과 재분석 |
| 결과 revision | 실행 참조, mask·측정·모델 목록, 완료·확인 상태 | 재분석 결과가 이전 결과를 덮어쓰지 않도록 관리 |
| 구조 인스턴스 | 안정적인 class ID, 환자 side, mask label·layer 대응, mesh 대응 | 같은 구조의 같은 쪽을 검사 간 연결 |
| 측정값 | 지표 ID, 값·단위·방법·상태·대상 영역, 결과 revision 참조 | 수치 의미와 비교 가능성 유지 |
| 파일 | 종류, 저장 참조, 크기·해시, 원본/파생 여부, 공간 변환 정보 | 손상·누락 확인, 모델과 수치의 혼합 방지 |

회원 계정과 환자는 동일한 개념으로 두지 않는다. 한 사용자가 여러 환자 자료를 볼 수 있고, 한 환자의 자료에 여러 사용자가 접근할 수 있으므로 소유·접근 관계를 별도로 정한다. 환자 본인의 로그인 기능은 아직 확정되지 않았다.

검사 촬영일, 앱으로 가져온 시각, 분석 실행 시각, 동기화 시각을 구분한다. Follow-up은 원칙적으로 검사 촬영일을 기준으로 정렬하며, 날짜나 환자 대응이 불명확한 데이터를 자동으로 기존 기록에 합치지 않는다.

### 6.1 결과를 함께 묶는 규칙

앱에서 실행한 분석의 완료 결과는 그 작업이 약속한 필수 출력과 입력·실행 버전을 함께 가리켜야 한다. 제공된 mask·측정값·GLB·구조 대응은 같은 실행에 연결한다. 외부 mesh만 열어보는 것과 분석 완료는 구분하며, 선택적 지방 계산의 미지원 때문에 이미 유효한 형태/부피 표시까지 막지 않는다. 작은 manifest로 관계를 표현하는 방향을 제안하되, 구체 파일명·JSON schema는 실제 출력 확인 후 정한다.

- mask와 측정값이 서로 다른 실행에서 나온 경우 하나의 정상 결과로 묶지 않는다.
- 재분석은 새 revision을 만든다. 기존 결과는 유지하고, 현재 열람·비교 대상으로 어떤 revision을 선택했는지 표시한다.
- 파일이 전부 저장·검증되기 전에 결과를 완료로 노출하지 않는다.
- 렌더링용 중심 이동·축 변환·스케일은 원본 물리 좌표와 구분해 기록한다.
- Demo 여부, 분석 완료 여부, 사람이 확인했는지는 서로 다른 상태다.

## 7. 공간 정보와 좌우 식별

### 7.1 현재 케이스에 확인된 것

저장소 README와 검증 코드에는 원본 NRRD와 export 프로그램을 대조한 기록이 있다. 해당 GLB는 NRRD LPS 좌표 `(x, y, z)`를 `(x, z, -y)`로 변환하고 중심을 이동한 결과이며, 환자의 왼쪽 방향이 +X로 유지된다. 현재 자산에서는 중심화된 X=0이 24개 paired class의 모든 triangle을 좌우로 구분한다. `iliac`, `mulifidus`, `rectus_abdominis`는 현재 방식으로 side를 부여하지 않는다. [현재 좌우 구현](../app/model-side.ts), [모델 검증](../scripts/validate-atlas.mjs)

이는 **현재 자산에 대해 검증된 조건**이다. 해당 세 class가 모든 검사에서 원래 좌우 구분이 불가능하다는 뜻도, 새 GLB의 X=0이 언제나 환자 정중면이라는 뜻도 아니다.

### 7.2 새 검사에 적용할 원칙

- 좌우는 화면의 왼쪽·오른쪽이 아니라 환자 기준이다.
- 원본 좌표계와 affine, source label의 side 정의를 보존한다. NRRD는 `space`, `space origin`, `space directions`, `space units` 등으로 공간 정보를 표현한다. [NRRD 형식 정의](https://teem.sourceforge.net/nrrd/format.html)
- 화면 중심 이동, 카메라 회전, Explode 이동, 개별 회전 후에도 구조 인스턴스의 side는 바뀌지 않는다.
- 새 데이터의 side는 모델 출력·label 대응과 환자 좌표 정보로 확인한다. 화면 중심이나 mesh 중심의 부호만으로 일반화하지 않는다.
- 하나의 class mesh에 양쪽이 합쳐져 있다면 export 단계에서 side별 식별 정보를 남기는 방식부터 검토한다. 정확한 방식은 원본 mask 구조에 맞춰 정한다.
- `left`, `right`뿐 아니라 `midline`, `unknown`, 좌우 구분 비대상 상태를 표현할 수 있어야 한다. 모르는 쪽을 임의로 Left에 넣지 않는다.

데이터 내부를 class+side 단위로 구성하더라도 기존 class 단위 선택 UX를 즉시 바꾸지 않는다. 한쪽만 선택·숨김·회전하는 기능은 별도 요구사항으로 결정한다.

## 8. 측정값과 차이의 정의

### 8.1 부피

표시 단위는 사용자 요구에 따라 `cm³`를 사용한다. 측정은 원본 mask와 그 mask가 놓인 물리 공간을 기준으로 한다. 뷰어에서 중심화·스케일 조정·평활화한 mesh를 기본 측정 근거로 사용하지 않는다.

균일한 affine 격자의 이진 mask에서, voxel 좌표를 mm 단위 물리 좌표로 보내는 3×3 행렬을 A라 하면 기본 관계는 다음과 같다.

```text
부피(cm³) = 구조에 속한 voxel 수 × |det(A)| / 1000
```

이 식은 격자·단위·mask 의미가 확인된 경우의 기준이다. 확률 mask, 비균일 간격, 겹치는 layer, resampling 등은 실제 계산 프로그램의 정의를 확인해야 한다. 기존 계산식을 받으면 대상 격자와 단위를 검증한 후 연결한다. 동일 값을 프런트엔드에서 다시 추정하지 않는다.

### 8.2 지방 관련 지표

현재 `Fat infil. %`는 UI용 가상 값이다. 실제 연결에서는 다음을 정해야 한다.

- 어떤 입력 영상·추가 series가 필요한가.
- 무엇을 지방침윤 또는 지방 관련 지표로 정의하는가.
- 어떤 영역·mask와 계산 방법을 사용하는가.
- 출력 단위·범위·산출 불가 조건은 무엇인가.

입력이나 산출 방법이 다른 지표를 이름만 같게 바꿔 한 추세선으로 합치지 않는다. CT와 MRI 결과도 동일 지표로 비교 가능한지 방법 확인이 먼저다. 본 문서는 지방침윤 산출 공식이나 임상적 기준을 새로 정하지 않는다.

### 8.3 현재 좌우 비교 규칙

| 항목 | 현재 표시 규칙 | 예외 |
| --- | --- | --- |
| 부피 좌우 차이 | `abs(L − R) / ((L + R) / 2) × 100` | 둘 다 0이면 상대 차이는 정의하지 않음 |
| 지방침윤 좌우 차이 | `abs(L − R)`, 단위 `pp` | 양쪽 값과 동일한 측정 방법이 있어야 계산 |
| hover 우선순위 | hover한 환자 쪽 → 반대쪽 → 차이 | side 불명확 시 임의로 hovered side를 강조하지 않음 |

위 수식은 현재 UI의 표시 관례다. 임상 판단 기준으로 확정한 것이 아니다. hover하는 쪽이 바뀌어도 현재 절대 좌우 차이의 크기는 바뀌지 않는다. [현재 수식](../app/demo-measurements.ts), [표시 구현](../app/measurements.tsx)

### 8.4 결측값과 신뢰할 수 없는 비교

- 값이 없으면 `—`와 이유를 표시하며 0으로 채우지 않는다.
- 미지원 구조, 촬영 범위 밖, 계산 실패, 한쪽만 존재, 지표 비대상을 구분한다.
- 실제로 계산된 0과 계산할 수 없어 반환된 0을 출력 상태로 구분한다.
- 부피가 음수이거나 값이 유한하지 않은 등 명백히 잘못된 입력은 정상 수치로 표시하지 않는다.
- 한쪽만 유효하면 해당 쪽 값은 보여줄 수 있지만 양쪽 차이는 계산하지 않는다.
- Demo와 실제 결과가 섞여 실제 환자의 정상 결과처럼 보이지 않게 한다.

## 9. Follow-up 비교

### 9.1 무엇을 서로 연결할 것인가

비교의 기본 키는 같은 환자, 같은 해부학적 class, 같은 환자 side, 같은 측정 지표다. 검사 날짜와 결과 revision은 각각 표시한다. 구조 이름만 같다는 이유로 서로 다른 환자나 다른 쪽의 값을 비교하지 않는다.

| 비교 | 기준 | 표시 |
| --- | --- | --- |
| 좌우 비교 | 같은 검사에서 Left 대 Right | 양쪽 값과 절대 차이 |
| 시점 비교 | 같은 구조·같은 쪽에서 이전 검사 대 현재 검사 | 이전·현재 값, 부호 있는 변화량과 변화율 |

제안하는 시점 비교 수식은 `현재 − 기준` 및 `(현재 − 기준) / 기준 × 100`이다. 기준값이 0이거나 없으면 상대 변화율을 표시하지 않는다. 지방 비율의 변화량은 pp와 상대 %를 혼동하지 않도록 명칭을 구분한다.

가상 예시: 왼쪽 대퇴직근 부피가 220 → 232 cm³이면 변화량은 +12 cm³, 상대 변화율은 약 +5.5%다. 이 예시는 현재 환자의 실제 결과가 아니다.

### 9.2 비교 화면 방향

초기 두 시점 비교 제안은 이후 **최대 3개 결과·다른 환자 비교·케이스 활성화·대응 구조 독립 회전** 요구로 확장되었다. 최신 동작 기준은 [개발 준비 문서 6.3절](EXMO_DEVELOPMENT_READINESS.md)의 확정 요구와 제안을 구분해 적용한다. 아래의 카메라 동기화 등은 초기 제안이며 사용자 확정 기능으로 간주하지 않는다.

- 동일 환자에서 기준 검사와 비교 검사를 선택한다.
- 두 검사 모델을 나란히 놓고, 같은 class를 확인할 수 있게 한다.
- 환자 방향이 맞춰진 상태에서 회전·확대를 동기화할 수 있게 한다.
- 양쪽 검사 날짜·modality·분석 revision을 구별되게 표시한다.
- 표와 그래프로 같은 쪽의 수치 변화와 같은 날짜의 좌우 차이를 구분해 보여준다.
- 한 검사에만 존재하는 구조나 수치를 숨기지 않고 해당 상태를 표시한다.

카메라 동기화는 영상 정합이 아니다. 보기 좋게 정렬된 두 모델을 voxel 수준으로 대응된 결과처럼 취급하지 않는다. 겹쳐 보기, 변형 지도, 동일 위치의 국소 변화 분석은 정합과 별도 검증이 필요한 후속 기능이다.

### 9.3 비교 가능성 확인

촬영 범위가 달라 근육 일부가 잘렸거나, 지표의 산출 방법·대상 영역·모델 버전이 달라졌다면 변화량의 의미가 달라질 수 있다. 결과에 이 정보를 남겨 비교 가능 여부와 이유를 표시한다. 준비되지 않은 보정 값을 만들어 정상 비교처럼 보이게 하지 않는다.

모델 업데이트 후 과거 검사를 재분석할 경우 새 revision을 보존하고, 가능한 경우 같은 분석 버전끼리 비교한다. 모델 변경으로 생긴 차이와 실제 환자의 변화를 자동으로 동일시하지 않는다.

## 10. 분석 실행과 저장의 동작

제안하는 작업 흐름은 입력 검증 → 대기 → 분석 → 측정·3D 생성 → 결과 확인 → 완료다. 실패와 취소는 별도 종료 상태로 기록한다. 실제 분석 프로그램이 알려주는 진행 정보만 사용하고, 근거 없는 정밀 진행률을 표시하지 않는다.

| 상황 | 필요한 동작 |
| --- | --- |
| 입력 조건 불일치 | 분석 전 원인과 지원 조건 표시, 원본 유지 |
| 모델 실행 실패·메모리 부족 | 단계와 재시도 가능 정보를 남기고 UI 유지 |
| 사용자 취소 | 작업을 종료하고 미완료 결과를 완료 목록에 넣지 않음 |
| 중간에 앱 종료 | 다음 실행에서 중단 상태를 식별, 이전 완료 결과 유지 |
| 저장 공간 부족·파일 누락 | 완료 전 검증, 불완전한 결과와 정상 결과 구분 |
| 재분석 | 새 실행·revision 생성, 이전 결과 보존 |

첫 구현에서는 중단된 계산을 정확히 그 지점부터 재개하는 기능까지 약속하지 않는다. 안전하게 중단 상태를 알리고 재실행할 수 있으면 된다. 분석과 결과 확인 상태는 로컬에 저장하고, 앱 메모리에만 두지 않는다.

## 11. 로컬 저장·서버 동기화·접근 권한

### 11.1 로컬과 서버의 역할

로컬 분석 경로를 선택한다면 네트워크가 끊겨도 이미 가진 입력의 분석·완료 결과 열람을 지원하는 방향을 제안한다. 서버 추론을 선택한 작업의 오프라인 실행까지 보장하는 것은 아니다. 로그인 유효 기간과 오프라인 허용 정책은 별도 결정한다.

로컬에는 환자·검사·작업 기록과 파일 참조를 저장한다. 서버에는 동기화 대상으로 선택된 결과를 저장한다. 원본 영상까지 보낼지, 결과 모델·측정값만 보낼지, 웹에서 원본 단면을 볼지는 비용과 제품 범위에 따라 결정한다. 사용자의 파일 가져오기가 원본 전체의 자동 업로드를 의미하지 않게 한다.

### 11.2 동기화의 최소 동작

1. 동기화할 환자·검사와 파일 범위를 식별한다.
2. 파일 전송과 무결성 확인 후 결과 참조를 완료로 등록한다.
3. 재시도가 동일 결과를 계속 복제하지 않게 안정적인 ID와 파일 해시를 사용한다.
4. 로컬 완료, 업로드 대기, 전송 중, 서버 완료, 실패 상태를 구분한다.
5. 서버에서 확인된 같은 결과 revision을 Web에서 연다.

서버 장애나 업로드 실패가 로컬 완료 결과를 지우지 않게 한다. 동기화는 백업과 동일하지 않으며, 로컬·서버 자료 삭제와 보존·복구 정책은 실제 저장 기능을 구현할 때 정한다. Git 커밋은 앱 코드의 이력이지 환자 영상·분석 결과의 백업이 아니다.

### 11.3 계정과 권한

회원가입만으로 모든 환자 자료를 볼 수 있게 하지 않는다. API와 파일 접근 모두에서 해당 사용자의 권한을 확인해야 한다. 모델 URL을 알아도 다른 기관·사용자의 자료를 가져갈 수 없는 구조로 둔다.

첫 제품에서 필요한 역할은 실제 사용자 구성을 확인해 정한다. 기관 관리자가 필요한지, 분석 담당자와 열람 담당자를 구분할지, 환자 본인에게 공유할지는 미결정이다. 처음부터 범용 권한 편집기를 만들 필요는 없지만 서버 측 접근 제어는 웹 기능의 첫 구현에 포함한다.

파일 업로드의 형식·크기·참조 경로를 검증하고, 민감한 원본 정보와 계정 토큰을 일반 로그에 그대로 남기지 않는다. 분석 프로그램 실행 시 파일명을 셸 명령으로 조립하지 않는다. 이는 실제 파일 가져오기·외부 프로그램 실행·회원 기능을 안전하게 연결하기 위한 구현 조건이다.

## 12. UI/UX와 기존 동작 보존

현재 Marimo 기반 시각 방향을 이어간다. 기본 배경 `#08081a`, 남색 `#111144`, 주황색 포인트 `#f98513`, Pretendard, 얇은 경계와 반투명 glass 패널을 기준으로 한다. 선택된 목록은 은은한 배경·경계로 표현하며, 사용자가 제거를 요청한 측면 강조 줄이나 장식용 아이콘을 다시 추가하지 않는다. [현재 스타일](../app/globals.css)

segment의 의미를 나타내는 Class 색상은 [app/anatomy.ts](../app/anatomy.ts)의 대응을 유지한다. Muscle preset의 뼈·근육 색상도 별개 선택으로 유지한다. UI 테마나 기관 브랜딩을 바꾸면서 모델 색상, 조명, 재질, 뷰어 배경을 함께 바꾸지 않는다. 투명한 모델은 배경의 영향을 받으므로 시각적 회귀 확인도 필요하다.

새 제품 화면은 환자·검사 목록, 분석 상태, 현재 검사 결과, 비교 화면을 중심으로 구성한다. 실제 사용 흐름이 정해지기 전에 사용하지 않을 대시보드·위젯·통계를 대량 추가하지 않는다.

hover는 빠른 확인을 위한 수단으로 유지하되, 같은 값은 측정 목록과 선택 상태에서도 접근할 수 있어야 한다. 새 기능에서도 키보드 접근, 확대 화면의 가독성, 동작 감소 설정을 유지한다.

## 13. 권장 개발 순서와 단계별 완료 기준

다음 순서는 구현 제안이다. 일정·인력·예산을 확정한 계획은 아니다.

이 표는 최초의 큰 제품 단계다. 실제 작업 분할과 현재 Desktop 구현을 반영한 P0–P8의 완료 조건은 [개발 준비 문서](EXMO_DEVELOPMENT_READINESS.md)를 사용한다.

| 단계 | 범위 | 완료 기준 | 먼저 필요한 것 |
| --- | --- | --- | --- |
| 0. 실제 결과 계약 확인 | 원본·mask·측정값·모델 출력 대조, ID·side·단위 정리 | 한 검사에서 결과와 원본의 대응을 설명·검증 가능 | 대표 입력, 실제 분석 출력, 계산 정의 |
| 1. 실제 결과 뷰어 연결 | 고정 case·Demo 의존 부분을 검사 결과 입력으로 전환 | 두 개 이상의 결과를 바꿔 열고 구조·수치가 섞이지 않음 | 단계 0의 데이터 |
| 2. Desktop 분석 경로 | 지원 입력 하나, 분석 실행·상태·취소·완료 저장·재열람 | 앱에서 가져온 실제 검사가 분석 후 다시 열림; 실패·재시도에도 이전 결과 유지 | 실행 가능한 모델, 대상 OS·실행 장비 |
| 3. Follow-up | 환자 이력, 기준·현재 검사 선택, 좌우·시점별 수치 비교, 나란히 보기 | 같은 환자의 두 시점을 같은 class·side로 비교; 결측·조건 차이 처리 | 대응이 확인된 두 시점 자료 |
| 4. 계정·Web 연결 | 회원·권한, 선택 동기화, 공통 뷰어로 열람·비교 | 허용된 계정에서 동일 revision 확인; 타 계정의 자료 접근 차단 | 서비스 사용자·소속·업로드 범위 결정 |
| 5. 지원 범위 확장 | 추가 modality·부위·모델, 정합·고급 비교 등 | 기능별 입력 조건·정확도·성능 기준 충족 | 실제 수요와 해당 모델·검증 자료 |

단계 1에서 기존 분석 결과를 먼저 연결하면 모델 실행과 UI 오류를 구분하기 쉽다. 첫 기능 완성 목표는 단계 2의 실제 단일 검사 흐름이며, Desktop·Web·follow-up을 포함한 제품 흐름은 단계 4까지 연결되어야 충족된다.

X-ray 3D 추정, 수동 segmentation 편집기, PACS 연동, 자동 판독, 범용 모델 마켓, 대규모 GPU 스케줄러는 첫 범위에 자동 포함하지 않는다. 각각 실제 요구와 입력·출력이 확인되면 별도 범위를 정한다.

## 14. 검증 계획

이 절은 향후 구현의 검증 기준이다. 아래 검증이 이미 실행되었거나 통과했다는 기록은 아니다. 기존 저장소 검증은 유지하고, 추가 기능의 실제 경계와 실패 조건을 확인하는 검증을 더한다.

| 검증 대상 | 확인할 내용 |
| --- | --- |
| 부피·단위 | 알려진 크기의 합성 mask에서 cm³ 변환 확인; 격자 변경 후 측정 대상 일치 |
| 공간·좌우 | 서로 다른 방향·원점의 입력, 카메라·Explode·회전 후에도 환자 side 유지 |
| class 대응 | 외부 label ID·표시명·mesh·측정 대상 일치; 지원하지 않는 class 식별 |
| 결측·비정상 값 | 0·결측·산출 실패·한쪽만 있음·비유한 값에서 잘못된 차이 계산 방지 |
| 실제 출력 연결 | 알려진 분석 결과와 뷰어 수치 일치, Demo 표시 전환이 출처에 맞음 |
| 검사 전환 | 이전 검사의 모델·hover·선택·비동기 로드 결과가 다음 검사에 섞이지 않음 |
| Follow-up | 다른 환자·side를 연결하지 않음; 날짜·기준값 0·버전 차이 처리 |
| 작업 실행 | 취소·실패·앱 종료·저장 실패 후 미완료 결과와 완료 결과 구분 |
| 동기화 | 중단·재시도·중복 요청·파일 누락에서 중복 및 잘못된 완료 표시 방지 |
| 접근 제어 | 다른 계정·기관의 검사와 파일을 API·직접 URL 모두로 차단 |
| 기존 뷰어 | 선택·그룹·1.7초 분해·0.7초 복귀·hover·색상 preset·접근성 회귀 확인 |
| 성능·배포 | 대상 장비에서 가져오기 시간, 분석 시간·메모리, 모델 로드, 상호작용 응답 확인 |

분석 정확도와 화면 표시의 정확도는 따로 검증한다. UI 검증이 통과해도 segmentation 모델의 성능을 검증한 것은 아니다. 모델별 정답 자료와 평가 기준은 해당 모델 및 사용 목적에 맞춰 정한다.

테스트 자료는 합성 또는 사용이 허용된 자료로 마련한다. 실제 환자 영상·모델 가중치·계정 비밀값을 애플리케이션 Git 저장소에 테스트 편의상 추가하지 않는다.

문서화를 완료하는 데 아래 답변이 필요하지는 않다. 해당 기능에 착수할 때 확인할 목록이다.

필요 자료는 다음 기능에 맞춰 받는다. 결과의 기본 형태 표시는 mesh·class 대응·출처로 시작할 수 있고, 실측·좌우·Overlay·물리 크기 비교에는 각 기능의 근거를 추가한다. 원본 검사·모델 실행 방법·리뷰 HTML을 모두 받아야만 표시 작업을 시작할 수 있는 것은 아니다. 모델 연동에는 실행 가능한 프로그램과 대표 입출력이, Follow-up에는 대응이 확인된 여러 시점 결과가 필요하다. 구체 구분은 개발 준비 문서 5.2절을 따른다.

이 저장소와 현재 데모만으로 실제 분석 정확도, 모든 영상에 대한 지원, 분석 소요 시간, 전체 개발 기간을 확정할 수는 없다. 앱 연결 구조는 구체화할 수 있으며, 불확실성은 위 자료를 연결하는 단계에서 줄인다.
