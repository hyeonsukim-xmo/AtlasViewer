# 솔루션 제품화 설계 재검토

검토일: 2026-10-17. 대상: [설계](EXMO_SOLUTION_PRODUCTIZATION_DESIGN.md), [구현 계획](EXMO_SOLUTION_PRODUCTIZATION_PLAN.md), [홈 모형](prototypes/solution-home.html). 제품 코드 기준 `d474eea`.

이 설계는 한 Desktop 앱에서 PC·YubiKey에 묶인 상품을 선택 설치하고, 별도 계정으로 기관 결과를 서버에 게시·열람하게 한다. 재검토에서 찾은 **계약 보완 4건과 추가 보완 3건을 사용자 지시에 따라 반영했다.** 1–5번은 설계/구현 계획 수정, 6–7번은 화면 모형 수정·실행 검증까지 완료했다. 실제 제품 서버 구현 완료를 뜻하지 않는다. 아래 발견 내용과 행 번호는 수정 전 기록이며, 현재 상태는 마지막 반영 표를 따른다.

검토 부하는 기관당 복수 사용자, PC 교체/백업 복구, 서로 다른 PC의 결과 게시, 병원망 중단 후 재개, 같은 결과의 Raw/후처리/늦은 3D 도착이다. 수치 부하 시험이나 실제 서버 보안 검증을 수행했다는 뜻이 아니다. 두 번째 재검토에서 발견한 5건과 수정 결과는 문서 마지막에 기록했다.

## 최초 검토: 먼저 고칠 항목

### 1. 재암호화 재시도와 게시 중복 방지 계약이 충돌한다 — P1

- **대상:** 설계 §8.2의 새 generation/DEK 규칙(283행), §9.1의 암호화 metadata 포함 manifest(315행), §9.2의 같은 key/다른 request hash는 409 규칙(323행).
- **역할:** 끊어진 업로드를 재개하면서 같은 결과를 두 번 만들지 않는 규칙이다.
- **문제/재현 상황:** 첫 업로드의 암호화 사본을 재사용할 수 없어 같은 Raw revision을 새 DEK로 다시 준비하면 암호문 hash와 wrapping metadata가 바뀐다. 게시 manifest 전체를 request hash로 구현하면 같은 idempotency key에 다른 내용이 되어 정상 재시도가 409로 막힌다. 현재 문서는 request hash의 정확한 범위와 upload session 재발급 규칙을 정하지 않았다.
- **최소 수정:** 분석 결과의 논리적 identity/content digest와 **전송 attempt/generation**을 분리한다. content digest는 확정된 측정·Mask·recipe 등 의미상 동일성을 나타내고 암호화 nonce/wrapped key/upload 시각은 제외한다. 같은 attempt의 재전송은 동일 암호문을 재사용하고, 재암호화는 새 attempt로 시작하되 서버의 결과 revision은 하나만 유지한다. 실제 분석 내용 변경은 계속 거부한다.
- **그대로 두면:** 일시적 통신/임시파일 장애가 수동 정리나 불필요한 재분석을 요구하는 게시 실패로 바뀐다.
- **필요 검사:** commit 응답 유실, staging 만료, 로컬 암호화 사본 재생성, 두 attempt의 동시 complete, 같은 identity에 다른 원문 모두 검사한다. 이것은 설계 계약 분석이며 구현된 서버에서 409를 실측한 것은 아니다.

### 2. PC 이전 시 결과 identity와 게시 장비 identity가 구분되지 않는다 — P1

- **대상:** 설계 §4.2의 이전/복구(87행), §9.2 idempotency key(323행), §11.2의 `(org, device, sourceResultId, revision)` unique(375행), §11.4 tombstone(408행).
- **역할:** PC를 옮겨도 동일 분석 결과를 이어서 관리하고, 삭제된 결과가 복원되는 것을 막는다.
- **문제/재현 상황:** PC A의 결과를 새 installation B에 복구한 뒤 게시할 때 device를 현재 게시 PC로 해석하면 unique key가 달라진다. 같은 결과가 두 번 생성되거나 A의 key에 기록된 삭제 tombstone을 우회한다. 반대로 device를 생성 당시 A로 해석하면, 회수된 A와 정상 게시자 B를 구분할 별도 필드/이관 규칙이 필요하다.
- **근거:** [현재 결과 저장소](../desktop/security/result-storage.cjs)의 `restore`는 저장소 ID를 유지하면서 새 installation의 수신키로 복구한다. 실제 PC 이전에서 분석 내용이 같아도 현재 installation은 바뀌는 경로가 존재한다.
- **최소 수정:** 결과 생성 시 고정된 `originResultId`/`originStoreId`와 `analysisRevision`을 보존하고, 현재 요청을 서명하는 `uploaderInstallationId`를 분리한다. 동일 기관 내 이관은 서버 승인된 origin 연결을 유지한다. dedup/tombstone은 안정된 origin 기준, 요청 인증은 현재 장비 기준으로 검사한다. 다른 기관 이관은 별도 승인된 새 소속 기록으로 처리한다.
- **그대로 두면:** PC 교체 후 중복 결과·중복 저장 비용이 생기고 삭제의 의미도 깨진다.
- **필요 검사:** A에서 게시 → B로 복구 → 재게시 시 같은 결과, A에서 삭제 → B 복구본 게시 거부, B의 위조 origin 주장 거부, 늦은 GLB도 동일 origin에 귀속.

### 3. 기존 결과의 3D 복구와 새로운 분석 권한이 충돌한다 — P1

- **대상:** 설계 §4.3 새 mesh를 `derive`로 분류(107행), §4.5 승인 작업의 완료/다른 worker 재사용 금지(127–129행), §6.1 과거 결과 reader 유지(178행).
- **역할:** 새 분석은 허가된 상품으로 제한하면서 이미 생성한 결과는 계속 읽게 한다.
- **문제/재현 상황:** 측정과 Mask까지 완료되고 3D 생성 중 앱이 종료된 뒤 상품이 만료되거나 모델을 제거한다. 재시작 후 동일 결과의 3D 재시도는 새 worker의 새 계산이므로 현재 `derive` 규칙으로는 막히지만, 과거 결과 열람/필수 후속 완료 정책으로는 보존해야 한다. durable 후속 허가에 대한 계약도 없다.
- **근거:** [imaging.cjs](../desktop/imaging.cjs)의 `queueMesh`(217행)와 `variant`의 failed/interrupted 복구(719–723행)가 이 경로다. [imaging-worker.py](../desktop/imaging-worker.py)의 finalize/mesh는 모델 추론과 다른 요청이며 현재는 보호 저장소 준비 여부를 검사한다(892–895행). 모델 허가 파서만 바꾸면 이 호출들을 해결하지 못한다.
- **최소 수정:** 기존의 확정된 Mask와 표시 recipe에서 동일한 3D를 생성/재시도하는 것은 **기존 결과 표시**에 포함한다. Mask를 바꾸는 새 후처리·재추론은 새로운 상품 실행 허가를 받는다. 표시 경로에서 원본/Mask/측정 값을 바꿀 수 없게 하고, 과거 viewer 의존성을 보존한다. 이렇게 하면 별도 영구 실행 허가 시스템을 추가할 필요가 없다.
- **그대로 두면:** 계약 만료나 모델 제거 후 3D를 복구할 수 없거나, 반대로 허가 없는 후처리를 열람 경로로 실행하게 된다.
- **필요 검사:** 앱 중단 → 만료/모델 제거 → 동일 3D 복구 허용, 기존 GLB 읽기 허용, 새 Mask 생성 후처리 거부. cloud 전송의 늦은 3D도 같은 결과 revision에 결합한다.

### 4. 대표 Overlay의 픽셀 안 식별정보 처리 규칙이 빠져 있다 — P1

- **대상:** 설계 §8.1 대표 Overlay 기본 허용(272행), header 전송 제외(274행), §8.4 허용 필드 정책(299행).
- **역할:** 필요한 결과만 게시하고 기관이 허용하지 않은 식별정보는 제외한다.
- **문제/재현 상황:** 환자 이름/번호가 영상 픽셀에 이미 찍힌 입력을 대표 Overlay로 생성하면 header를 빼도 그 문자가 이미지에 남는다. 현재 [preview](../desktop/imaging-worker.py)는 픽셀 window/resize/overlay 합성을 수행하며 이름 제거를 하지 않는다(431–468행). 파일 항목 선택과 일반 임상 검토만으로는 픽셀 식별정보가 승인됐는지 판정할 수 없다.
- **최소 수정:** 대표 영상도 게시 manifest의 식별정보 정책 대상에 넣는다. V1은 게시 전 이미지 확인·필요 영역의 비가역 픽셀 제거·승인 기록으로 충분하다. 확인 불가/미승인 영상은 제외하고 측정/QC/허용 3D만 게시한다. 기관이 허용하는 식별정보를 유지하는 경우에도 명시적 정책/승인 범위를 기록한다. 원본과 분석 Mask는 바꾸지 않는다.
- **그대로 두면:** 가명 case label만 게시한다고 생각했는데 이미지 안에는 실제 환자번호가 전달될 수 있다.
- **필요 검사:** 합성 식별문자를 넣은 영상, header만 제거한 영상, 제거한 대표 영상, 영상 게시 제외 경로. CSS로 가리기/OCR 성공을 비식별 완료와 동일시하지 않는다.

픽셀 안 식별정보는 DICOM의 Clean Pixel Data 항목에서도 별도 처리 대상으로 다룬다. 원본을 편집하라는 의미가 아니라, 외부에 보낼 표시 사본의 승인 범위를 명확히 하자는 수정이다. [DICOM PS3.15 E.3.1](https://dicom.nema.org/medical/dicom/current/output/chtml/part15/sect_E.3.html)

## 최초 검토: 추가로 고칠 항목

### 5. 전체 확률 배열을 기본 전송 범위에서 빼야 한다 — P2

- **대상:** 설계 §8.1 `Native mask·확률/내부 QC 배열`을 묶은 기본 전송 행(269행).
- **역할:** 원격 열람과 결과 보관에 필요한 데이터를 지정한다.
- **문제/재현 상황:** 현재 [CT 원본 복원](../desktop/model-runner.py)의 `ct_inverse`는 33채널 native 확률을 제한된 block에서만 처리하고 uint8 label과 QC를 남긴다(246–306행). 이 표를 모든 배열 전송 요구로 해석하면 저장하지 않던 확률 배열까지 보존/생성해야 한다. 33채널 float32는 같은 voxel 수의 uint8 Mask보다 비압축 크기가 132배다. 실제 업로드 크기를 측정한 수치는 아니다.
- **최소 수정:** 기본 allowlist는 native Mask, 측정/QC 요약, 표시 3D, 승인 대표 영상으로 제한한다. 확률/entropy/disagreement 원시 배열은 기본 제외하고, 이미 있는 데이터에 대한 구체적인 검토 용도가 있을 때 별도 정책으로 추가한다. 없는 배열을 공유 때문에 재추론해 만들지 않는다.
- **그대로 두면:** 요청한 원격 열람에 필요 없는 계산·전송·보관 비용이 붙고 현 성능 최적화와 충돌한다.
- **필요 검사:** 확률 파일이 없는 기존 CT 결과 게시 성공, 숨겨진 전체 배열/임시파일 미전송, 제품 계산 경로 변경 없음.

### 6. 웹 모형에서 재로그인하면 Desktop 홈으로 들어간다 — P2

- **대상:** [solution-home.html](prototypes/solution-home.html) `header`(39행), `sign-in`/`account` 처리(54행). 구현 계획 P6은 이 모형을 통합 기준으로 사용한다.
- **역할:** 로그인 뒤 사용하던 제품 화면으로 돌아간다.
- **문제/재현 상황:** `웹/태블릿 열람` 선택 → 상단 계정에서 로그아웃 → 상단 로그인 → 가상 로그인 완료. `page`가 login에서 home으로 바뀌면서 CT/MRI/X-ray 분석 홈이 나타난다. 제품 종류를 현재 page 하나로 추론하기 때문이다. 실제 제품의 권한 우회가 아니라 **모형에서 재현한 화면 경계 오류**다.
- **최소 수정:** `surface=desktop|remote`와 페이지를 구분하고 로그인 복귀 위치를 해당 surface의 허용 경로로 제한한다. 실제 Web 빌드에 분석 코드를 포함하지 않는 기존 경계도 유지한다.
- **그대로 두면:** 구현 기준 모형이 읽기 전용 Web 요구와 다른 흐름을 제시한다.
- **필요 검사:** Web/태블릿에서 상단/본문 로그인·취소·세션 만료·재로그인 후 Desktop 메뉴 부재. 기존 15개 검사는 초기 remote 진입만 확인했다.

### 7. 비교할 수 없는 지표 조합에도 비교 버튼이 활성화된다 — P2

- **대상:** [solution-home.html](prototypes/solution-home.html) `resultTable`(42행), `resultAction`(53행), `compare-open`(54행), 설계 §10의 비교 제약.
- **역할:** 호환되는 최대 3개 결과의 같은 지표를 비교한다.
- **문제/재현 상황:** 일상 홈 → 비교 선택 → CT DEMO-001과 X-ray DEMO-002 선택. 선택 개수만 검사해 비교 버튼이 활성화된다. 눌렀을 때 지표 제한을 설명하는 알림만 나오며 선택 단계의 규칙이 없다. 실제 계산/비교를 수행한 것은 아니지만 모형이 잘못된 가능 상태를 보여준다.
- **최소 수정:** 결과의 지표 종류·단위·ontology/계산법 등 호환성을 검사해 선택 이유/거부 이유를 표시하고 시작 시 재검사한다. modality만 같다고 호환으로 보거나 modality만 다르다고 모든 열람을 막지 않는다. 다른 지표를 나란히 읽는 기능과 수치 비교는 구분한다.
- **그대로 두면:** 비교 버튼이 사용 불가능한 조합을 안내하거나, 구현 단계에서 면적과 체적을 같은 비교 표에 넣을 수 있다.
- **필요 검사:** 호환 2/3개 허용, cm²/cm³ 비교 거부, 같은 modality의 다른 지표 거부, 해제 후 호환 상태 복구. 기존 검사는 행 하나의 선택만 확인했다.

## 검증 기록과 판정

- 현재 실행/결과 worker, variant/mesh 재시도, 결과 키 복구, CT block 복원, preview 픽셀 경로를 대조했다.
- Electron offscreen으로 6·7번을 실제 재현했다. 가상 데이터만 사용했고 외부 요청은 차단했다. 증거: `outputs/solution-design-review/findings.json`, `remote-login-regression.png`; 재현 스크립트 `outputs/solution-design-review/reproduce.cjs`.
- 1–5번은 설계 계약과 코드 연결 검토 결과다. 아직 없는 cloud API에 대한 실행 결과처럼 보고하지 않는다.
- 확률 배열을 기본에서 제외하고 표시용 3D를 별도 유료 계산 권한에서 빼면 구현 범위를 줄일 수 있다. 삭제 가능한 제품 코드 줄 수는 아직 구현 전이므로 산정하지 않는다.

**최초 판정: 1–4번 계약을 먼저 수정하고, 5–7번을 전송/홈 구현 전에 반영한다.** 라이선스와 계정 분리, 원본 로컬 보관, 기관 소유, 선택 설치, Web 읽기 전용이라는 큰 구조는 유지한다.

최초 리뷰는 발견 기록만 저장했다. 아래는 후속 수정 내역이다.

## 두 번째 재검토·수정 — 2026-10-17

기존 30개 검사가 통과해도 아래 경로에는 문제가 남아 있었다. 설계 계약 1건과 모형 동작 4건을 구분해 검토했고, 사용자 지시로 모두 보완했다. 이 절의 번호는 두 번째 리뷰의 1–5번이다.

| 번호 | 발견한 문제와 재현 조건 | 수정 | 검증/남은 gate |
| --- | --- | --- | --- |
| 1 | 같은 origin/revision/content를 A workspace에 게시한 뒤 B로 요청하면, 대상 일치 조건 없이 A의 기존 결과를 반환할 수 있는 계약 | 첫 성공 commit의 workspace를 고정. begin/조회/complete/중복 반환/첨부에서 일치 검사. 다른 대상은 `PUBLICATION_TARGET_MISMATCH`로 거부하고 비공개 기존 결과 정보를 반환하지 않음. 동시 commit과 tombstone에도 동일 규칙 | 설계 §9/§11, 계획 P5 및 SYN-18–19 반영. 실제 서버 시험은 구현 후 수행 |

수정 전 재현 증거는 `outputs/solution-design-rereview/findings.json`과 `reproduce.cjs`다. 이 스크립트는 **이전 결함을 확인하는 기록**이며 수정 후 통과 검사로 사용하지 않는다. 회귀 검사를 먼저 추가했을 때 `published result appears in Desktop cloud results without losing navigation`에서 실패하는 것을 확인한 뒤 모형을 수정했다.

수정 후 [check-home.cjs](prototypes/check-home.cjs): **42개 검사 통과, 외부 요청 0건, 화면 8장 생성**. 새 Desktop 서버 목록, 비교 중 결과 열기 버튼, 820 px 태블릿 화면을 직접 확인했다. 최신 `outputs/solution-design-check/verification.json`은 현재 모형의 SHA-256과 42개 통과 항목을 포함한다. 계획의 VIEW-10–11에 제품 통합 시 같은 검사를 수행하도록 기록했다.

**판정: 이번 5건의 설계·모형 수정 완료.** 실제 서버의 workspace 충돌 처리는 계약과 검증 계획까지 반영한 상태이며, 실행 코드가 구현됐다는 뜻은 아니다. 기존 분석 앱·모델·계산 설정·환자 데이터는 변경하지 않았다.
