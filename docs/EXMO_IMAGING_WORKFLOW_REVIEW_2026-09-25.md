# EXMO 영상 가져오기·분석·최대 3개 결과 비교 기능 검토

- 작성일: 2026-09-25 (Asia/Seoul)
- 문서 성격: 사용자 요구사항 정리 및 구현 검토
- 상태: 검토 단계. 아래 기능의 개발·배포 완료를 의미하지 않음
- 코드 검토 기준: AtlasViewer `design/marimo-glass`, 문서 커밋 `cbaa6e7` 시점의 앱 코드
- 관련 문서: [EXMO Desktop·Web 구현 방향](https://github.com/hyeonsukim-xmo/AtlasViewer/blob/cbaa6e7/docs/EXMO_PRODUCT_ARCHITECTURE.md)

이 문서는 사용자가 설명한 실제 사용 흐름과 그에 대한 기술 검토를 기록한다. **사용자가 명시한 요구사항, 구현 제안, 아직 결정하지 않은 정책을 구분한다.** 이번 작업은 문서 저장이며, 앱 기능 수정이나 모델 연결을 시작하라는 지시로 해석하지 않는다.

## 1. 제품 범위와 전체 흐름

현재는 웹 데모로 제공하고, 이후 Desktop App으로 발전시키는 방향이다. 기존 3D 뷰어 앞에 영상 가져오기·프로토콜 검토·영상 리뷰·분석 결과 확인 단계를 연결하고, 마지막 뷰어에서 최대 3개의 결과를 비교한다.

```text
DICOM / NRRD / NIfTI / 압축 NIfTI 가져오기
  → 메타데이터 추출 및 환자·Study·Series 정리
  → 기존 classification 모델로 프로토콜 분류
  → SeriesDescription 검토 및 사용할 영상 선택
  → hover 미리보기 / 선택한 preview의 slice 스크롤
  → 선택 영상들을 바둑판 카드로 리뷰
  → 방향 전환 및 불필요한 영상 선택 해제
  → 최종 분석 입력 확정
  → Segmentation 및 관련 측정
  → Value 목록 / 선택한 구조의 Overlay / 지방 관련 지표 확인
  → 기존 3D 렌더링 화면
  → 최대 3개 결과 선택 및 케이스·구조물 비교
```

NIfTI의 일반적인 단일 파일 확장자는 `.nii`이며 압축 파일은 보통 `.nii.gz`를 사용한다. 사용자가 언급한 `nifti`, `nifti.gz`는 해당 형식군을 가리키는 것으로 정리한다. 실제 지원 여부는 확장자만이 아니라 파일 내용을 확인해 판단해야 한다. [NIfTI 형식 정의](https://github.com/NIFTI-Imaging/nifti_clib/blob/master/niftilib/nifti1.h)

## 4. 환자·검사·시리즈·결과의 식별

### 4.1 SeriesDescription은 표시용 설명이다

시리즈를 묶는 기준은 설명 문자열이 아니라 StudyInstanceUID와 SeriesInstanceUID다. SeriesDescription은 비어 있거나 다른 시리즈에서 반복될 수 있다. 같은 설명이 있다고 합치거나 설명이 다르다고 다른 환자로 분리해서는 안 된다. [DICOM 시리즈 정의](https://dicom.nema.org/medical/dicom/current/output/chtml/part03/sect_C.7.3.html)

같은 Series에 속한 파일이라도 중복 instance, 서로 다른 프레임·시간·방향 등이 있는지 입력 조건에 따라 확인해야 한다. 파일명이나 InstanceNumber만으로 모든 볼륨의 순서를 확정하지 않는다.

### 4.2 비교 선택의 단위

사용자가 말한 case를 다음 중 무엇으로 저장·선택할지 명확히 해야 한다.

- 환자 A의 첫 검사와 추적 검사는 서로 다른 비교 대상이다.
- 같은 환자·같은 Study의 1mm, 5mm, iMAR 시리즈도 각각 분석 결과를 만들 수 있다.
- 같은 입력을 다른 모델 버전으로 재분석한 결과도 구분해야 한다.

**권장 비교 단위는 특정 환자·검사에 연결된 하나의 분석 결과 revision이다.** 카드에는 환자 또는 case 이름, 검사일, StudyDescription, SeriesDescription을 함께 보여준다. 분석이 여러 입력 series를 필요로 한다면 해당 입력 묶음을 결과에 연결한다.

최대 3개 제한은 마지막 3D 비교 대상으로 이해한다. 가져올 파일 수나 리뷰 카드 수까지 3개로 제한하는 요구사항은 확인되지 않았다.

### 4.3 NRRD·NIfTI의 메타데이터 차이

affine·spacing 같은 공간 정보가 있다고 해서 원래 DICOM의 환자명·StudyDescription·SeriesDescription이 모두 보존되어 있다는 뜻은 아니다. NRRD는 추가 key/value를 가질 수 있고 NIfTI도 확장 정보를 가질 수 있으나, 변환 과정에서 어떤 정보를 남겼는지 확인해야 한다. [NRRD 형식 정의](https://teem.sourceforge.net/nrrd/format.html), [NIfTI 헤더 정의](https://github.com/NIFTI-Imaging/nifti_clib/blob/master/niftilib/nifti1.h)

첨부된 카드 화면처럼 원본 메타데이터 JSON을 함께 가져오는 경로가 유용하다. 공간 정보만 있는 입력에는 없는 검사 설명을 추정해 넣지 않고, 누락을 표시하거나 명시적인 연결 과정을 둔다. NRRD가 원본 intensity 영상인지 segmentation labelmap인지도 구분해야 한다.

## 5. 프로토콜 분류와 분석 적합성

기존 classification 모델을 우선 활용한다. 앱에서 별도의 분류 모델이나 키워드 분류기를 새로 만드는 것을 기본 방향으로 잡지 않는다.

연결 전에 확인할 계약은 다음과 같다.

| 항목 | 확인할 내용 |
| --- | --- |
| 입력 | 설명 문자열, DICOM 메타데이터, 대표 slice, 전체 볼륨 중 무엇을 요구하는가 |
| 출력 | 프로토콜 class, 모델 사용 가능 여부, 점수, 추가 조건이 무엇인가 |
| 지원 범위 | modality·부위·촬영 조건·외부 데이터 범위 |
| 연결 | 분류 결과가 어떤 segmentation 모델·설정으로 이어지는가 |
| 불확실성 | 분류 불가·애매한 결과를 어떻게 표현하는가 |
| 실행 | 프로그램 호출 방식, 의존 환경, CPU/GPU·메모리 요구 |

표시 상태는 `사용 가능 / 검토 필요 / 미지원`으로 구분하는 방안을 제안한다. 이는 모델 출력에 맞춰 결정해야 하며, 모델 점수를 검증된 확률처럼 단정하지 않는다. 수동 선택 변경을 허용한다면 원래 분류와 사용자 변경을 함께 기록한다.

분류가 적합해도 파일 누락, 잘못된 볼륨 구성, 지원 범위 밖의 크기·촬영 영역 등으로 실행할 수 없을 수 있다. **프로토콜 분류와 입력 데이터 검증을 별도로 수행한다.** 수동 선택이 데이터 손상이나 필수 입력 누락까지 해결하는 것으로 취급해서는 안 된다.

Segmentation과 지방 관련 측정이 같은 입력을 사용하는지도 확인해야 한다. 추가 series가 필요한 계산이라면 해당 series를 한 작업의 입력으로 연결하고 공간 대응을 검증한다. 기존 계산식·모델이 제공되기 전에는 자동으로 모든 지표가 산출된다고 가정하지 않는다.

## 6. hover·고정 preview·바둑판 리뷰

### 6.1 미리보기 상태

hover 대상, 클릭해서 고정한 preview, segmentation 실행 대상으로 선택한 영상은 서로 다른 상태로 관리하는 방향을 제안한다. 잠시 hover한 영상이 자동으로 분석 대상에 추가되어서는 안 된다.

필요한 동작은 다음과 같다.

- hover는 임시 미리보기, 클릭은 preview 고정으로 구분한다.
- 목록에서 오른쪽 preview로 마우스를 이동해도 영상이 갑자기 사라지지 않게 한다.
- A→B 순서로 빠르게 이동했을 때 늦게 끝난 A 로딩이 B 화면을 덮어쓰지 않게 한다.
- slice 스크롤은 대상 preview 안에서만 처리하고 페이지 스크롤과 충돌하지 않게 한다.
- 카드별 현재 방향·slice·window 설정을 유지한다.
- 로딩 전·실패·영상 없음 상태를 이전 영상과 명확히 구분한다.

고정 preview가 있는 동안 다른 SeriesDescription을 hover하면 잠시 교체할지, 별도 임시 preview로 보여줄지는 아직 미결정이다. 어느 방식을 택하든 hover 종료 후 돌아갈 대상이 명확해야 한다.

### 6.2 바둑판 카드

선택된 영상들을 카드로 나열하고 case 이름·검사일·StudyDescription·SeriesDescription·기본 방향·preview를 표시한다. 분석에 필요한 경우 두께·실제 간격·크기·분류 결과도 확인할 수 있게 한다.

우클릭 선택 해제는 분석 대상에서 제외하는 동작으로 정의하는 방안을 제안한다. 원본 파일 삭제로 연결하지 않는다. 우클릭을 쓰기 어려운 입력 환경을 위해 체크박스나 해제 버튼도 제공할 수 있다.

분석 실행은 선택 상태와 구분된 명시적 실행 동작을 두는 편을 권장한다. 카드 선택 해제 즉시 다음 단계로 자동 진행할지는 사용자와 아직 결정하지 않았다.

### 6.3 방향 전환은 MPR이다

Axial에서 Sagittal·Coronal로 바꾸는 것은 2D preview를 회전시키는 일이 아니라 볼륨에서 다른 방향의 단면을 생성하는 MPR이다.

- 위치·방향·spacing을 반영해 실제 비율로 표시한다.
- 원래 촬영면과 표준 해부학적 방향을 구분한다. 비스듬히 촬영한 경우도 고려한다.
- 방향을 바꿀 때 같은 물리적 위치를 최대한 유지한다.
- 환자 기준 L/R·A/P 등 방향 표기를 일관되게 유지한다.
- Slice Thickness를 실제 슬라이스 간격으로 그대로 사용하지 않는다. 영상 위치 정보도 확인한다.

DICOM은 pixel spacing, image orientation, image position, slice thickness와 slice spacing을 구분한다. [DICOM 영상 평면 정의](https://dicom.nema.org/medical/dicom/current/output/chtml/part03/sect_C.7.6.2.html)

5mm 간격 데이터를 보간해 부드럽게 표시해도 원래 없던 1mm 수준의 정보를 얻는 것은 아니다. 단일 2D X-ray처럼 볼륨이 없는 입력에는 같은 방식의 다른 방향 단면을 제공할 수 없으므로 토글 지원을 입력에 맞춰 제한한다.

Cornerstone3D 같은 기존 영상 도구는 방향별 영상, labelmap Overlay, viewport별 도구 설정을 제공하므로 후보로 검토할 만하다. 영상 preview·Overlay와 기존 Three.js 구조물 뷰어를 나누는 방향을 제안하며, 라이브러리 채택은 아직 확정하지 않았다. [Cornerstone3D 공식 문서](https://www.cornerstonejs.org/docs/getting-started/overview/)

## 7. 웹 데모의 메모리와 모델 실행 위치

첨부 화면에 있는 `512 × 512 × 687` 볼륨을 16비트 단일 채널로 가정하면 픽셀 배열만 약 **343.5 MiB**다. 같은 크기 세 개는 **1,030.5 MiB**, 약 1 GiB다. 이는 조건부 계산이며 실제 파일의 datatype을 확인한 결과는 아니다.

압축 파일, 압축 해제 버퍼, 데이터형 변환, segmentation mask, GPU 복사본은 별도 메모리를 사용할 수 있다. 바둑판 카드마다 전체 볼륨을 상시 보유하는 방식은 피해야 한다.

권장 방향은 다음과 같다.

1. 메타데이터와 가벼운 대표 이미지를 먼저 표시한다.
2. 현재 리뷰하는 영상에 필요한 데이터를 우선 로드한다.
3. 화면 밖 카드와 더 이상 사용하지 않는 영상의 무거운 처리를 중단·해제한다.
4. 압축 해제·영상 처리가 UI 조작을 막지 않도록 작업을 분리한다.
5. 캐시 크기와 동시 로딩 수는 대상 장비에서 측정해 제한한다.

분류 모델이 전체 볼륨을 요구한다면 해당 작업에는 전체 로딩이 필요하다. 이 경우에도 모든 preview 카드가 독립적으로 같은 데이터를 중복 보유할 필요는 없다.

웹에서 파일을 선택하는 것과 서버로 파일을 전송하는 것은 별도 동작이다. UI에서 분석 실행 위치와 전송 범위를 분명히 해야 한다. 기존 모델이 Python/GPU 환경을 요구하면 서버 또는 로컬 분석 프로그램과의 연결이 필요할 수 있다. 브라우저 안에서 실행할 수 있는지는 실제 모델과 실행 환경을 확인한 뒤 판단한다.

정적 웹사이트만으로 기존 모델을 그대로 실행할 수 있다고 가정하지 않는다. 웹 데모와 Desktop에서 공통으로 사용할 것은 입력·결과의 의미와 UI이며, 실행 경로는 실제 모델 조건에 맞춰 정한다.

## 8. Value·Overlay·지방 관련 결과의 연결

```text
확정한 입력 묶음
  → 분석 실행 ID와 버전
  → segmentation mask + 측정 결과 + 표시용 3D
  → 같은 결과 revision을 사용하는 Value / Overlay / 3D 화면
```

분석 과정의 crop, resampling, 축 변환, 중심 이동 정보를 보존해야 한다. 배열 크기가 같아도 원점·방향·spacing이 다르면 원본과 mask는 맞지 않을 수 있다. label mask를 다시 샘플링할 때에는 label을 보존하는 처리가 필요하다. [SimpleITK 공간·재표본화 설명](https://simpleitk.readthedocs.io/en/master/fundamentalConcepts.html)

수치 행을 클릭하면 해당 결과의 class·side에 대응하는 Overlay를 열도록 한다. 구조가 현재 slice에 없으면 구조가 보이는 대표 위치로 이동시키는 방안을 제안한다. 정확한 이동 기준은 centroid 또는 구조를 충분히 보여주는 단면 등 실제 결과에 맞춰 정한다.

지방침윤은 값만 제공되는지, 지방 분포 영상 또는 별도 mask도 제공되는지에 따라 화면이 달라진다. 계산 방법·원본 입력·출력 단위가 확인되어야 한다. 계산할 수 없는 값을 0으로 채우거나 Demo 값을 실제 검사 결과로 대체하지 않는다.

분석 시작 시 입력 목록을 확정해서 저장한다. 진행 중인 작업의 입력을 UI 선택 변경에 따라 조용히 바꾸지 않는다. 여러 작업 중 하나가 실패해도 다른 완료 결과는 유지하고, 미완료·실패·완료 상태를 구분한다. 재분석 결과는 새 revision으로 기록한다.

## 9. 최대 3개 비교의 상호작용 규칙

### 9.1 두 단계의 활성화

케이스 활성화와 구조물 선택을 별도 상태로 두는 방향이 적절하다. 아래는 사용자의 의도를 구현 가능한 규칙으로 정리한 **제안**이며, 모든 세부 동작이 사용자에게 확정된 것은 아니다.

| 현재 상태 | 입력 | 제안 동작 |
| --- | --- | --- |
| 최대 3개 전체 보기 | 케이스 A 클릭 | A 활성화, 다른 케이스를 투명하게 표시 |
| A 활성화·구조물 미선택 | 배경 클릭 | 케이스 활성화 해제, 전체 비교 상태로 복귀 |
| A 활성화·조립 상태 | 구조물 클릭 | 기존 개별 class 복수 선택·재클릭 해제 적용 |
| A의 구조물 선택 중 | 배경 클릭 | 구조물 선택을 먼저 해제하고 A 활성화 유지 |
| A 활성화 | Explode | A 구조물들을 펼침 |
| A 펼침 상태 | Femur 선택 | A·B·C의 대응 Femur를 나란히 표시 |
| 대응 구조물 비교 중 | 해당 구조물 위 우클릭 드래그 | 드래그를 시작한 구조물만 자기 중심에서 회전 |
| 구조물 비교 해제 | 배경 클릭 등 | 각각의 회전을 약 0.7초 동안 원래 방향으로 복귀 |

배경 클릭은 현재 선택된 가장 안쪽 단계부터 해제하는 방식이 예측 가능하다. 직전에 사용자가 어떤 조작을 했는지 복잡한 이력 조건을 추가하기보다 현재 케이스·구조물 선택 상태로 판단하는 방안을 제안한다.

### 9.2 입력 충돌과 투명도

- 바둑판 카드의 우클릭 해제와 3D 구조물의 우클릭 드래그 회전을 영역별로 구분한다.
- 비활성 케이스를 클릭했을 때는 케이스 활성화가 먼저인지 구조물 선택까지 동시에 할지 정한다. 우선 케이스만 활성화하는 편을 권장한다.
- 투명한 다른 케이스가 활성 케이스의 구조물 선택을 가로채지 않게 hit 대상 우선순위를 정한다.
- 케이스를 흐리게 하는 opacity와 구조물 선택의 주변 opacity를 무작정 곱해 구조물이 거의 사라지지 않게 한다.
- 비교 대상·활성 케이스·선택 구조물·드래그 중인 실제 인스턴스를 구분한다.
- 드래그가 화면 밖에서 끝나거나 취소되어도 회전 대상이 계속 잡힌 상태로 남지 않게 한다.

케이스 간 구별은 이름·날짜·일정한 위치와 표식으로 제공한다. 케이스마다 segment 색상을 바꾸는 방식은 기존 색상 보존 요구와 맞지 않는다.

## 10. 현재 3D 코드에서 변경이 필요한 부분

### 10.1 개별 모델의 동일 높이 정규화

현재는 `scale = 2.4 / 모델 높이`로 각 모델을 같은 높이에 맞춘다. 이를 서로 다른 케이스에 각각 적용하면 실제로 작은 구조물과 큰 구조물이 같은 크기로 보일 수 있다. [현재 스케일 처리](https://github.com/hyeonsukim-xmo/AtlasViewer/blob/cbaa6e7/app/scene.tsx#L507)

비교 시 기본은 같은 mm 축척을 사용하는 방향을 제안한다. 모델별로 크기를 맞추는 대신 공통 카메라·표시 범위를 조정한다. 형태 비교를 위해 크기를 정규화하는 기능이 필요하면 별도 모드로 명시한다. 데이터에 물리 단위와 export 변환이 없다면 실제 크기 비교라고 표시할 수 없다.

자세 차이, 촬영 범위 차이, 실제 크기 차이를 구분해야 한다. 예를 들어 한 검사에서 구조물 일부가 잘려 있다면 작은 부피를 곧바로 전체 구조물의 크기 차이로 해석하지 않는다.

### 10.2 우클릭 회전 대상

현재 코드는 우클릭한 위치와 무관하게 선택된 class를 회전시킨다. 세 케이스 비교에서는 드래그 시작 위치의 실제 구조물을 판별하고, 드래그 종료까지 그 대상을 유지해야 한다. [현재 회전 대상 결정](https://github.com/hyeonsukim-xmo/AtlasViewer/blob/cbaa6e7/app/scene.tsx#L329)

각 구조물 인스턴스가 별도의 pivot·회전 상태를 가져야 한다. 식별 키도 class만으로는 부족하며 분석 결과·class·side 또는 구조 인스턴스를 함께 식별해야 한다. 기존 회전·복귀 동작은 재사용할 수 있다. [현재 회전 구현](https://github.com/hyeonsukim-xmo/AtlasViewer/blob/cbaa6e7/app/segment-rotation.ts)

### 10.3 양쪽 class와 한쪽 구조물의 차이

현재 Femur는 좌우가 같은 class에 묶여 있다. 다음 두 동작은 별개다.

- A·B·C의 양쪽 Femur를 각각 한 묶음으로 비교·회전.
- A·B·C의 왼쪽 Femur만 비교하고 각각 해당 뼈의 중심에서 회전.

어느 단위를 사용할지 결정해야 mesh 식별·회전 중심·측정 표·hover 동작이 명확해진다. 데이터에 side 정보를 마련하는 것과 UI를 즉시 한쪽 선택으로 바꾸는 것은 별도 결정이다.

한 케이스에 대응 구조물이 없으면 빈 비교 자리와 이유를 표시하고, 다른 구조물을 대신 대응시키거나 결과를 만들어 채우지 않는다.

## 11. 나란히 비교와 정합 기반 비교

| 기능 | 필요한 수준 |
| --- | --- |
| 같은 class·side의 구조물을 나란히 표시 | 안정적인 구조 식별, 방향·단위 확인, 공통 축척 |
| 나란히 놓인 구조물을 독립 회전 | 인스턴스별 picking·pivot·회전 상태 |
| 같은 환자의 두 시점 수치 비교 | 동일 대상·지표·방법·비교 가능한 촬영 범위 |
| 다른 환자의 수치 비교 | 케이스 차이로 명시, 지표·대상 범위 일치 확인 |
| 같은 해부학적 위치로 slice 동기화 | 검사 간 위치 대응 또는 정합 |
| 겹쳐 보기·국소 변화 표시 | 정합 방법과 별도의 정확도 검증 |

같은 환자의 두 검사라도 slice 번호가 같다고 같은 위치가 아니다. 다른 환자는 물리 좌표 숫자가 같아도 같은 해부학적 위치가 아니다. 카메라 방향을 맞추는 것 역시 영상 정합과 다르다.

첫 비교 범위는 같은 class·side를 나란히 표시하고 실제 축척·수치를 함께 보는 방향을 권장한다. 겹치기, 변형 지도, 정확한 위치별 변화 분석은 후속 범위로 분리한다.

Follow-up은 기준 검사 대비 시간에 따른 변화로 표시하고, 다른 환자의 결과는 케이스 간 차이로 표시한다. 세 개 비교에서는 기준 하나와 나머지 두 개를 비교하는 방식을 제안한다. 양쪽 차이와 시점별 차이도 혼동되지 않게 한다.

## 13. 후속 확인 자료와 검증 순서

### 13.1 필요한 자료

- 제공 예정인 시리즈 리뷰 HTML: 실제 이벤트와 메타데이터 구조를 확인한다. 스타일을 그대로 이식하는 용도는 아니다.
- classification 모델의 실행 방법과 입력·출력 예시.
- segmentation 및 지방 지표 계산의 입력·출력 예시와 좌표 변환 정보.
- 여러 Series가 있는 대표 Study 및 대응 메타데이터 JSON.
- 같은 환자의 두 시점과 별도 환자의 비교 가능한 결과 샘플.

이 목록은 이후 기능 설계·구현에 사용할 자료이며, 이번 문서 저장을 완료하기 위한 추가 요청은 아니다.

### 13.2 우선 검증할 사례

1. 같은 SeriesDescription을 가진 서로 다른 Series가 섞이지 않는지 확인한다.
2. NRRD·NIfTI의 설명 정보가 없거나 원본 JSON과 연결되지 않을 때 잘못된 환자·Study로 묶이지 않는지 확인한다.
3. 방향·원점·spacing이 다른 영상에서도 좌우와 MPR 비율, Overlay 위치가 맞는지 확인한다.
4. hover를 빠르게 이동하거나 검사 로딩을 취소해도 이전 영상이 현재 preview를 덮어쓰지 않는지 확인한다.
5. 선택 변경·취소·분석 실패 후에도 작업 입력과 결과가 정확히 대응하는지 확인한다.
6. 세 결과의 실제 크기 차이가 개별 정규화 때문에 사라지지 않는지 확인한다.
7. 케이스 활성화·구조물 선택·배경 클릭·Explode의 상태 전환이 제안 규칙과 일치하는지 확인한다.
8. 구조물 A에서 시작한 우클릭 드래그가 B·C를 회전시키지 않는지, 해제 시 각 구조물이 원래 방향으로 복귀하는지 확인한다.
9. 구조물 누락·한쪽만 존재·측정 불가·비교 조건 차이를 잘못된 0이나 가상 결과로 표시하지 않는지 확인한다.
10. 대상 장비에서 큰 볼륨·여러 카드·세 3D 결과의 메모리와 조작 응답을 측정한다.

첫 검증은 모델 입출력과 원본 좌표 대응을 확인하는 작은 실제 데이터 흐름부터 시작하는 것을 권장한다. 그 다음 preview 리뷰, 분석 결과 연결, 3개 비교를 확장한다. 모델의 정확도 검증과 앱의 표시·조작 검증은 별도로 수행한다.
